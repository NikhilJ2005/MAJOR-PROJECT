\begin{center}
    {\Large Abstract}
\end{center}
\vspace{0.6cm}
\begin{onehalfspace}
A single call to a large language model (LLM) can answer a question, but most useful work takes several steps. The program has to decide what to do next, try again when something fails, and remember what it has already done. Fixed prompt chains cannot loop, and fully autonomous agents are hard to predict or debug. LangGraph, an open-source library from LangChain, offers a middle route. The developer describes the application as a graph: each node is a step, each edge is a move to the next step, and all nodes share one state object. The model does its thinking inside the nodes, while the graph decides the order.

This seminar studies LangGraph through the paper by Duan and Wang, \emph{Exploration of LLM Multi-Agent Application Implementation Based on LangGraph+CrewAI} (arXiv:2411.18241). The authors pair LangGraph, which controls the flow, with CrewAI, which groups role-based agents into a team. They illustrate the pairing with three cases: an email assistant, a code generation and review loop, and a system that audits and forwards work orders. The report explains LangGraph's core ideas, reviews six related papers, walks through the paper's architecture and workflow, and discusses its strengths, weaknesses and uses. One point stands out. The paper's results are case studies rather than measurements, so its claims of better efficiency still need to be tested.
\end{onehalfspace}

\vspace{0.5cm}
\noindent\textbf{Keywords:} LangGraph, CrewAI, Large Language Models, Multi-Agent Systems, Agent Orchestration.

\chapter{Introduction}

Large language models have changed quickly. A few years ago they mostly answered questions. Today they can plan, write code, look things up and call other programs. The trouble starts when you try to build something real with one. Take a support bot. It has to work out what the customer wants, send the request to the right place, fetch details from a database and check the reply before sending it. A code assistant has to write code, run it, read the error and try again, sometimes many times over.

Work like this does not run in a straight line. It \textbf{branches}: a billing question goes one way and a technical one goes another. It \textbf{loops}: try again until the tests pass. And it needs \textbf{memory}, because later steps depend on earlier results. The two usual ways of building LLM applications both struggle here. A \emph{chain} runs a fixed list of steps in order. It is predictable, but it cannot go back and it keeps no shared state. A \emph{free-running agent} lets the model decide everything, including which tool to call and when to stop. It is flexible, but hard to test, and one bad decision can throw the whole run off course.

LangGraph is built for the space between these two. It is an open-source library from LangChain, released in 2024 under the MIT licence, with versions for Python and JavaScript/TypeScript \cite{langgraphdocs}. Its design borrows from graph-processing systems such as Google's Pregel \cite{malewicz2010pregel}. The developer draws the application as a graph. Nodes are steps of work, edges are the moves between them, and every node reads from and writes to one shared state. The developer fixes which paths are allowed, and the model does the work inside each step. LangGraph works with many model providers and is used for single agents, teams of agents, retrieval pipelines and workflows that pause for a human to approve.

The base paper for this seminar, by Duan and Wang \cite{duan2024langgraphcrewai}, asks what happens when LangGraph is combined with CrewAI \cite{crewaidocs}, a framework that organises agents into role-based teams. In their design LangGraph handles the flow: which step runs next, when to branch, when to loop, and what goes into the state. CrewAI handles the teamwork: which agent takes which task and how the agents cooperate. The authors show the combination on an email assistant, a code generation and review loop, and a ticket-handling system.

\section*{Objectives of the Seminar}
\begin{itemize}
    \item To explain why multi-step LLM applications need explicit control, and where chains and free-running agents fall short.
    \item To describe LangGraph's main building blocks: state, nodes, edges, conditional edges and checkpoints.
    \item To review earlier work on LLM agents and multi-agent systems.
    \item To study the LangGraph+CrewAI architecture, workflow and case studies in the base paper.
    \item To weigh up the advantages, limitations and uses of graph-based agent orchestration.
\end{itemize}

The report is organised as follows. Chapter~2 reviews the literature and Chapter~3 introduces the tools. Chapter~4 explains the method used in the base paper and Chapter~5 discusses its results. Chapters~6 to 8 cover advantages, disadvantages and applications, and Chapter~9 concludes.

% ================================================================== Chapter 2
\chapter{Literature Survey}

This chapter looks at six papers that shaped thinking about LLM agents. For each one I describe the method, what it showed, and the limitation that matters most when you want a multi-agent system you can actually control.

\section{ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al., 2023)}

ReAct \cite{yao2023react} lets the model switch back and forth between three kinds of output. A \emph{thought} is the model reasoning about what to do. An \emph{action} is a tool call, such as a Wikipedia search. An \emph{observation} is what the tool returned. Because the model can look things up mid-way, it relies less on guesswork, and ReAct did better than reasoning-only or acting-only baselines on HotpotQA, ALFWorld and WebShop. Most tool-using agents today follow this pattern. Its weakness is structural. The whole run is one linear loop with no saved state, so an early mistake carries forward and can spoil everything after it.

\section{Reflexion: Language Agents with Verbal Reinforcement Learning (Shinn et al., 2023)}

Reflexion \cite{shinn2023reflexion} lets an agent learn from failure without retraining the model. After a failed attempt the agent writes a short note in plain language about what went wrong. The note is kept in memory and given to the agent on its next try. This simple idea brought large gains on coding and decision-making tasks. The catch is that the agent needs a clear signal of whether it succeeded, which many real tasks do not provide. Every retry also costs more model calls and more time.

\section{AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation (Wu et al., 2023)}

AutoGen \cite{wu2023autogen}, an open-source framework from Microsoft, builds an application out of several agents that solve a problem by talking to each other. An agent can be backed by a model, by tools, by a person, or by a mix of these, so the framework is very flexible. The cost of that flexibility is control. The order of work comes out of the conversation itself, so it is hard to say in advance what the system will do, and agents can go in circles or wander off the task.

\section{MetaGPT: Meta Programming for a Multi-Agent Collaborative Framework (Hong et al., 2024)}

MetaGPT \cite{hong2024metagpt} copies how a software company works. Standard operating procedures (SOPs) are written into the prompts. Agents take roles such as product manager, architect and engineer, and pass structured documents along an assembly line, checking each other's work. The paper showed that this structure cuts down the inconsistencies seen when agents simply chat. The pipeline is fixed, though, and built mainly for software projects, and running many agents uses a lot of tokens.

\section{A Survey on Large Language Model based Autonomous Agents (Wang et al., 2023)}

Wang et al.\ \cite{wang2023survey} surveyed the rapidly growing work on LLM-based agents. They proposed a common framework of four modules: \emph{profile} (the agent's role), \emph{memory}, \emph{planning} and \emph{action}. They also reviewed applications and evaluation methods. The survey is a useful map of the field. As a survey, however, it offers no implementation or orchestration tool, and the field moves faster than any survey can keep up with.

\section{Agent AI with LangGraph: A Modular Framework for Enhancing Machine Translation Using LLMs (Wang and Duan, 2024)}

In an earlier paper by the same two authors \cite{wang2024translation}, LangGraph reads the input text and passes it to a specialised translation agent, with separate agents for English, French and Japanese built on models such as GPT-4o. It is a clear, concrete example of LangGraph's routing. The evaluation is small, though: it covers only a few languages and depends on a paid model.

\section*{Summary}

Put together, these papers show steady progress. ReAct gave agents the ability to act, Reflexion the ability to learn from mistakes, AutoGen the ability to converse, and MetaGPT the ability to follow procedures. They also show a gap that keeps coming back. Either the flow is rigid and cannot branch or loop, or it is left to the model and becomes hard to control. What is missing is a way for the developer to lay out the allowed paths, with shared state, loops and recovery, while the model still does the clever work at each step. LangGraph, and the LangGraph+CrewAI pairing in the base paper, aim at that gap.

\chapter{Materials and Methods}

The base paper does not train a model or use a dataset. Its materials are the frameworks and tools the system is built from. This chapter introduces them, along with the criteria the paper uses to judge the result.

\section{LangGraph: Core Concepts}

LangGraph builds stateful, multi-step LLM applications as graphs \cite{langgraphdocs}. The base paper highlights three things it adds over other LLM frameworks: loops, fine-grained control over the flow, and memory that persists between steps \cite{duan2024langgraphcrewai}. It supports several shapes of workflow, including single-agent, multi-agent, hierarchical and sequential. Its building blocks are listed below and drawn in Fig.~\ref{fig:graph}.

\begin{itemize}
    \item \textbf{State:} the shared data, usually a typed dictionary, that every node reads and updates. A reducer can say how an update is merged; for example, a new message can be appended to a list instead of replacing it.
    \item \textbf{Node:} an ordinary Python function that does one step of work, such as calling the model or a tool, and returns the part of the state it changed.
    \item \textbf{Edge:} a fixed move: after node A, run node B.
    \item \textbf{Conditional edge:} a small router function that looks at the state and picks the next node. Branches and loops are built from these.
    \item \textbf{START and END:} the graph's entry and exit points.
    \item \textbf{Checkpointer:} saves the state after every step. A run can then be paused, inspected, resumed after a crash, or continued once a person has approved it.
\end{itemize}

A LangGraph application is built in five steps: define the state, add nodes as functions, connect them with edges, compile the graph, and run it. The short example below answers a question with a single model call.

\begin{lstlisting}
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):          # 1. define the state
    question: str
    answer: str

def answer(state: State):        # 2. a node is a plain function
    return {"answer": llm.invoke(state["question"])}

g = StateGraph(State)
g.add_node("answer", answer)
g.add_edge(START, "answer")      # 3. connect the edges
g.add_edge("answer", END)
app = g.compile()                # 4. compile
app.invoke({"question": "What is LangGraph?"})   # 5. run
\end{lstlisting}

\section{CrewAI Framework}

CrewAI \cite{crewaidocs} is an open-source framework for coordinating role-playing agents that work on a problem together. Each agent is given a role, a goal and a set of tools. The framework has four building blocks:

\begin{itemize}
    \item \textbf{Agent:} a unit that can carry out tasks, make decisions and talk to other agents. It is described by a role, a goal and a short backstory.
    \item \textbf{Task:} a piece of work for an agent, with a description, the agent responsible and the tools it may use.
    \item \textbf{Tool:} something an agent can use, such as reading email or searching documents.
    \item \textbf{Crew:} a team of agents, plus the process that decides the order in which their tasks run.
\end{itemize}

CrewAI can use model APIs such as OpenAI's as well as locally run models through Ollama \cite{ollamadocs}. It supports agents with custom roles, automatic hand-off of tasks between agents, and flexible task management \cite{crewaidocs}. It is designed for multi-step work, decision-making and problem-solving.

\section{Evaluation Criteria}

The base paper is an exploratory case study. It reports no accuracy, speed or cost figures. Instead it judges the LangGraph+CrewAI pairing qualitatively, on four points that I also use in this report:

\begin{itemize}
    \item \textbf{Control:} can the developer define and restrict the flow of the application?
    \item \textbf{Information flow:} how easily do state and results pass between steps and agents?
    \item \textbf{Collaboration:} how well is the work split among agents with different roles?
    \item \textbf{Extensibility:} how easily can existing tools and agents, such as those built with LangChain, be plugged in?
\end{itemize}

\chapter{Methodology}

\section{Design Rationale}

The base paper starts from a simple observation. A single LLM agent cannot handle complex tasks well, and a team of agents only works if two things are in place: tight control of the flow and good teamwork \cite{duan2024langgraphcrewai}. Instead of asking one framework to do both, the authors give each job to the tool that suits it. LangGraph's graph structure provides the control and moves information between agents. CrewAI's role-based crews decide who does what. The paper asks two questions: how to design agents on LangGraph so that the flow is precisely controlled, and how CrewAI can make those agents capable of a wider range of tasks.

\section{System Architecture}

The architecture has two layers that meet at the shared state (Fig.~\ref{fig:arch}).

\begin{itemize}
    \item \textbf{LangGraph, the control layer.} The user's task enters the graph. Nodes stand for agent steps, and edges with conditional routing decide which step runs next. The shared state carries data between steps.
    \item \textbf{CrewAI, the team layer.} Inside a node, a crew of agents does the actual work. Each agent has a role and a goal, tasks are assigned to agents, and the agents work together to produce the node's result.
\end{itemize}

\section{Integrating LangGraph with CrewAI}

According to the authors, the combined framework makes complex tasks easier to manage. Flexible workflows, cooperation between agents and graph-structured management together improve how tasks are carried out, and the framework can be connected to existing tools. CrewAI keeps the work organised by assigning tasks clearly and defining roles. Because CrewAI also works with LangChain, developers who already have LangChain agents can bring them in without rewriting them \cite{duan2024langgraphcrewai}.

In practice the split is easy to state:
\begin{itemize}
    \item \textbf{LangGraph decides the flow:} the order of steps, the branches, the loops and the state.
    \item \textbf{CrewAI decides the teamwork:} which role-based agent takes which task, and how the agents cooperate.
\end{itemize}

\section{Workflow}

Fig.~\ref{fig:workflow} follows a task through the combined system. LangGraph receives the task and routes it to the next node. The CrewAI crew in that node carries out the work, and the result is written back to the shared state. A conditional edge then checks whether the job is finished. If not, the flow moves to the next step; if it is, the graph ends.

\section{Worked Example: Automatic Email Handling}

To make the method concrete, the authors take the email example from CrewAI's documentation and rebuild it on LangGraph+CrewAI \cite{duan2024langgraphcrewai}. The job is split into small steps and run automatically.

Fig.~\ref{fig:email} shows the graph. It starts at \texttt{check\_new\_emails}. A conditional edge then either continues to \texttt{draft\_responses}, if new mail has arrived, or goes straight to \texttt{wait\_next\_run}. After waiting, the graph returns to check the inbox again. That loop is what turns a one-off script into an assistant that keeps running, and it is something a plain chain cannot express.

from langgraph.graph import StateGraph
from .state import EmailsState
from .nodes import Nodes
from .crew.crew import EmailFilterCrew

class WorkFlow():
    def __init__(self):
        nodes = Nodes()
        workflow = StateGraph(EmailsState)
        workflow.add_node("check_new_emails", nodes.check_email)
        workflow.add_node("wait_next_run", nodes.wait_next_run)
        workflow.add_node("draft_responses", EmailFilterCrew().kickoff)
        workflow.set_entry_point("check_new_emails")
        workflow.add_conditional_edges(
            "check_new_emails",
            nodes.new_emails,
            {"continue": 'draft_responses', "end": 'wait_next_run'})
        workflow.add_edge('draft_responses', 'wait_next_run')
        workflow.add_edge('wait_next_run', 'check_new_emails')
        self.app = workflow.compile()

\chapter{Results and Performance}

The base paper presents its results as worked cases. It shows that the LangGraph+CrewAI design can be used to build working multi-agent applications and describes what the pairing improves. This chapter goes through those cases, lists the main findings, and then looks at what the results do and do not prove.

\section{Application Case 1: Code Generation with Code Review}

The authors used LangGraph+CrewAI to build an application that writes code and then reviews it (Fig.~\ref{fig:codegen}). A question goes to a \emph{code generation} node, which writes the code. A \emph{code check} node then tests it. If the check fails, the flow goes back to generation along with the feedback. If it passes, the code is returned as the answer. Because the status of each attempt and the feedback are shared through the graph state as they happen, the authors report that code generation became more efficient \cite{duan2024langgraphcrewai}. This is the same write, test and fix cycle that Reflexion and ReAct argue for. The difference is that here the loop is a visible edge in the graph rather than something left to the model.

\section{Key Findings}

From these cases the authors draw four conclusions:
\begin{itemize}
    \item \textbf{Efficient information flow:} LangGraph's graph structure makes it easier to pass information between agents.
    \item \textbf{Precise control:} building agents on LangGraph gives the developer close control over the multi-agent workflow.
    \item \textbf{Better collaboration:} CrewAI's task allocation and resource management improve teamwork and overall performance.
    \item \textbf{Complex tasks:} by splitting the work and cooperating, the agents handle tasks that a single agent finds hard.
\end{itemize}

\section{Discussion}

The base paper does a good job of showing \emph{how} LangGraph and CrewAI fit together. Its three cases make the division of work easy to grasp: the graph decides what happens next, and the crew decides who does it. The examples are practical, too. Sorting email, reviewing code and handling tickets are everyday jobs in many organisations.

The results need to be read carefully, though. The paper reports no measurements at all: no success rates, no response times, no costs, and no comparison with a single agent or with another framework. When the authors say efficiency ``improved'', they are describing what they saw in their cases, not the outcome of an experiment. A useful next step would be to test the pairing on a benchmark, measuring task success, the number of model calls and the cost against a single agent and against LangGraph on its own. Even with that gap, the paper is a clear and readable guide to building multi-agent applications in which control and teamwork sit in separate, well-defined layers.

% ================================================================== Chapter 6
\chapter{Advantages}

\begin{itemize}
    \item \textbf{Explicit control:} the developer decides which paths the application can take. The model fills in each step but cannot invent a new route, so the behaviour is easier to predict and to audit.
    \item \textbf{Shared state:} every step sees the same, up-to-date data, so nothing has to be copied between agents or squeezed into prompts.
    \item \textbf{Loops and retries:} a step can repeat until a condition is met, for example regenerating code until the tests pass. A plain chain cannot do this.
    \item \textbf{Persistence:} because the state is saved after every step, an application can pause, resume and recover from a failure without starting again \cite{langgraphdocs}.
    \item \textbf{Human-in-the-loop:} the graph can stop at any node and wait for a person to check or edit the state, which matters for actions such as sending an email.
    \item \textbf{Easy to debug:} each node is a normal function that can be tested on its own, and tracing tools such as LangSmith \cite{langsmith} show exactly which path a run took.
    \item \textbf{Works with many models:} both LangGraph and CrewAI can use several providers, including local models through Ollama.
    \item \textbf{Clear teamwork with CrewAI:} roles, goals and tasks give each agent a defined job, and existing LangChain agents can join a crew with little extra work.
\end{itemize}

% ================================================================== Chapter 7
\chapter{Disadvantages}

\begin{itemize}
    \item \textbf{Learning curve:} graphs, typed state, reducers and checkpointers take time to learn, and using two frameworks means learning two sets of ideas.
    \item \textbf{More code for simple jobs:} a task that a basic chain handles in a few lines needs more setup as a graph.
    \item \textbf{Large graphs get messy:} with many nodes and conditional routes, the flow becomes hard to picture and reason about.
    \item \textbf{Cost and delay:} loops and multiple agents mean more model calls, which raises both the cost and the response time.
    \item \textbf{Still depends on the model:} the graph limits the routes, but a poor model output can still pick the wrong route or produce a weak result inside a node.
    \item \textbf{Fast-changing tools:} both frameworks change their APIs between versions, so code and tutorials go out of date quickly.
    \item \textbf{No numbers in the base paper:} the benefits are shown through cases only, so they are not yet backed by measured results.
\end{itemize}

% ================================================================== Chapter 8
\chapter{Applications}

\begin{itemize}
    \item \textbf{Customer support:} a router node classifies each query and sends it to a billing agent, a technical agent or a person, keeping the conversation in the shared state.
    \item \textbf{RAG question answering:} the graph fetches documents, scores how relevant they are and, if they are poor, rewrites the query and searches again before answering.
    \item \textbf{Code generation and bug fixing:} write, test and fix in a loop, as in the base paper's code review case and in the authors' later study of automated bug fixing with LangGraph \cite{wang2025bugfix}.
    \item \textbf{Machine translation:} text is routed to language-specific translation agents \cite{wang2024translation}.
    \item \textbf{Data analysis:} separate agents build and run machine learning pipelines on Apache Spark \cite{wang2024spark}.
    \item \textbf{Multi-agent teams:} crews for research, writing and review, with one role per agent, as proposed in the base paper \cite{duan2024langgraphcrewai}.
    \item \textbf{Ticket and workflow automation:} checking, classifying and forwarding work orders, with similar past cases found in a vector database.
\end{itemize}

% ================================================================== Chapter 9
\chapter{Conclusion}

LangGraph turns an LLM application into a clear graph of steps that share one state. It adds what simple chains lack, namely branches, loops, memory and human control, while avoiding the unpredictability of fully autonomous agents. The developer decides which paths are allowed, and the model does the thinking within each step.

The base paper by Duan and Wang shows what happens when this idea is combined with CrewAI. LangGraph manages the flow and the state, CrewAI organises role-based agents into teams, and together they take on tasks that a single agent struggles with. The email assistant, the code review loop and the ticket system make the approach concrete and show that it fits ordinary, everyday problems.

The paper's main weakness is its evaluation. Its benefits are shown through cases rather than experiments, so the efficiency gains it describes still need to be confirmed with proper benchmarks of success rate, cost and response time. Future work could also look at how such systems behave as the number of agents grows, and how to keep large graphs easy to understand.

Overall, graph-based orchestration is fast becoming a common way to build dependable agentic AI. Studying it closely for this seminar showed me why: when the structure is explicit, the model's mistakes become much easier to find, contain and fix.

\chapter{Viva Questions and Answers}

\subsection*{Common Viva Questions}
\begin{enumerate}[leftmargin=*, itemsep=6pt]
    \item \textbf{What is LangGraph?}\\
    \textit{Answer:} An open-source library from LangChain for building stateful, multi-step LLM applications as a graph. Nodes are steps, edges are the moves between them, and all nodes share one state object.

    \item \textbf{How is LangGraph different from a LangChain chain?}\\
    \textit{Answer:} A chain runs a fixed sequence of steps in one direction. A LangGraph graph can branch with conditional edges, loop back to earlier steps, keep shared state and save checkpoints, so it can retry, pause and resume.

    \item \textbf{What are state, nodes and edges?}\\
    \textit{Answer:} The state is shared data, usually a typed dictionary, that every node reads and updates. A node is a function that does one step. An edge is a move between nodes; a conditional edge uses a router function to pick the next node from the current state.

    \item \textbf{What is a checkpointer and why is it useful?}\\
    \textit{Answer:} It saves the graph state after every step. A run can then resume after a crash, be inspected for debugging, or wait for a person's approval before continuing.

    \item \textbf{What does CrewAI add to LangGraph in the base paper?}\\
    \textit{Answer:} Role-based teamwork. Agents are given roles, goals and tools, and tasks are shared among them. LangGraph controls the order of steps and the state, while a CrewAI crew does the work inside a node.

    \item \textbf{Explain the email example from the base paper.}\\
    \textit{Answer:} The graph starts at \texttt{check\_new\_emails}. If there is new mail it continues to \texttt{draft\_responses}, which runs a CrewAI crew; otherwise it goes to \texttt{wait\_next\_run}. After waiting, it loops back to check again.

    \item \textbf{What tools did the authors use besides LangGraph and CrewAI?}\\
    \textit{Answer:} LangSmith to track and audit workflows, an Ollama embedding model to turn work-order text into vectors, and FAISS as the vector database for fast retrieval.

    \item \textbf{How does LangGraph compare with AutoGen?}\\
    \textit{Answer:} In AutoGen the order of work comes out of the agents' conversation, which is flexible but hard to predict. In LangGraph the developer lays out the allowed paths, so the behaviour is easier to control and debug.

    \item \textbf{What are the limitations of the base paper?}\\
    \textit{Answer:} Its results are case studies. It gives no measurements of accuracy, cost or speed and no comparison with a baseline, so the reported efficiency gains are not yet backed by experiments.

    \item \textbf{Where can LangGraph be applied?}\\
    \textit{Answer:} Customer support routing, RAG question answering, code generation and bug fixing, machine translation, data analysis pipelines, multi-agent research and writing teams, and ticket automation.
\end{enumerate}
