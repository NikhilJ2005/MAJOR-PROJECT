\begin{center}
    {\Large Abstract}
\end{center}
\vspace{0.6cm}
\begin{onehalfspace}
You can ask a large language model (LLM) a question and get a decent answer. Ask it to do a real job and it usually needs several steps. It has to decide what to do next, try again when something breaks, and remember what it did earlier. A fixed chain of prompts cannot loop back. A fully autonomous agent can, but it is hard to predict and harder to debug. LangGraph, an open-source library from LangChain, takes a middle path. The developer draws the application as a graph. Nodes are steps, edges are the moves between them, and every node shares one state. The model thinks inside the nodes, and the graph decides the order.

This seminar looks at LangGraph through a paper by Duan and Wang, \emph{Exploration of LLM Multi-Agent Application Implementation Based on LangGraph+CrewAI} (arXiv:2411.18241). They let LangGraph control the flow and CrewAI organise agents into role-based teams, and they show the idea on an email assistant, a loop that writes and reviews code, and a system that checks and forwards work orders. The report covers LangGraph's core ideas, six related papers, the paper's architecture and workflow, and its strengths, weaknesses and uses. One thing stood out to me. The paper's results are case studies, not measurements, so its claims about efficiency are still untested.
\end{onehalfspace}

\vspace{0.5cm}
\noindent\textbf{Keywords:} LangGraph, CrewAI, Large Language Models, Multi-Agent Systems, Agent Orchestration.

\chapter{Introduction}

Ask a large language model a question and you get an answer. Ask it to do a job, and things get harder. Real jobs come in steps.

Think about a support bot for a college website. A student types ``my fee receipt is wrong''. The bot has to work out that this is a billing problem, not a login problem, and send it to the right place. It then pulls the student's record, writes a reply and checks the reply before it goes out. A coding assistant has it worse. It writes some code, runs it, reads the error, and tries again. Sometimes that takes five rounds.

In other words, real work branches and loops, and the program has to remember what happened two steps back. Neither of the usual ways of building LLM apps copes well with that. A \emph{chain} runs its steps in a fixed order, top to bottom. You always know what it will do next, which is nice, but it can never go back, and its steps keep no common memory. A \emph{free-running agent} is the opposite: the model decides everything, even when to stop. You get flexibility. You also get something that is hard to test, where one wrong guess in the first minute can spoil the whole run.

LangGraph sits between these two. It is an open-source library from LangChain, released in 2024 under the MIT licence, with Python and JavaScript/TypeScript versions \cite{langgraphdocs}. Its design borrows ideas from graph-processing systems such as Google's Pregel \cite{malewicz2010pregel}. You draw your application as a graph. Each node is a step. Each edge says where to go next. Every node reads from, and writes to, one shared state. The developer decides which paths exist, and the model does the thinking inside each step. It works with many model providers, and people use it for single agents, agent teams, retrieval pipelines and flows that wait for a human to say ``yes''.

The base paper for this seminar is by Duan and Wang \cite{duan2024langgraphcrewai}. Their question is simple: what happens if you put LangGraph together with CrewAI \cite{crewaidocs}, a framework for building teams of agents with roles? In their design, LangGraph runs the flow. It picks the next step, decides when to branch or loop, and keeps the state. CrewAI runs the team. It decides which agent does which task. The authors try this on three problems: an email assistant, a loop that writes and reviews code, and a ticket-handling system.

\section*{Objectives of the Seminar}
\begin{itemize}
    \item Explain why an LLM app with many steps needs explicit control, and why chains and free agents are not enough on their own.
    \item Describe the building blocks of LangGraph (state, nodes, edges, conditional edges, checkpoints).

% ================================================================== Chapter 2
\chapter{Literature Survey}

I picked six papers for this survey. Each one changed how people build LLM agents, and together they explain why a tool like LangGraph was needed. For each paper I note what it does, what it showed, and where it falls short if you want a team of agents you can actually control.

\section{ReAct: Synergizing Reasoning and Acting in Language Models (Yao et al., 2023)}

ReAct \cite{yao2023react} has the model take turns between three kinds of output. First a \emph{thought}, where it reasons about what to do. Then an \emph{action}, such as a Wikipedia search. Then an \emph{observation}, which is whatever the tool sent back. Being able to look things up halfway through means less guessing. ReAct beat reasoning-only and acting-only baselines on HotpotQA, ALFWorld and WebShop, and most tool-using agents today follow the same pattern. The weak spot is the structure. The whole run is one straight loop with no saved state. If the model makes a mistake early, that mistake rides along to the end.

\section{Reflexion: Language Agents with Verbal Reinforcement Learning (Shinn et al., 2023)}

Reflexion \cite{shinn2023reflexion} lets an agent learn from failure without retraining the model. When an attempt fails, the agent writes itself a short note, in plain English, about what went wrong. On the next try it reads the note first. That small trick gave large gains on coding and decision tasks. The catch is the success signal. Reflexion only works when the agent can tell clearly whether it succeeded, and many real tasks never give you that. Every retry also costs extra model calls.

\section{AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversation (Wu et al., 2023)}

AutoGen \cite{wu2023autogen} comes from Microsoft. You build an app out of several agents that solve the problem by chatting with each other. An agent can be a model, a tool, a person, or a mix. That makes AutoGen very flexible. But the order of work comes out of the conversation itself, so you cannot say in advance what the system will do. In practice agents can go round in circles or drift away from the task.

\section{MetaGPT: Meta Programming for a Multi-Agent Collaborative Framework (Hong et al., 2024)}

MetaGPT \cite{hong2024metagpt} copies a software company. The authors write standard operating procedures (SOPs) into the prompts. Agents play a product manager, an architect and an engineer, and pass structured documents down an assembly line, checking each other's work as they go. It showed that structure cuts down the mess you get when agents just chat. Still, the pipeline is fixed and built mainly for software projects. Running that many agents also burns a lot of tokens.

\section{A Survey on Large Language Model based Autonomous Agents (Wang et al., 2023)}

Wang et al.\ \cite{wang2023survey} tried to map the whole area. They suggest that any LLM agent can be described with four parts: a \emph{profile} (its role), \emph{memory}, \emph{planning} and \emph{action}. They also review where agents are used and how they are tested. I found it the most useful paper for getting the big picture. Being a survey, though, it gives you no tool to build with, and new agent papers appear faster than any survey can keep up.

\section{Agent AI with LangGraph: A Modular Framework for Enhancing Machine Translation Using LLMs (Wang and Duan, 2024)}

This earlier paper by the same two authors \cite{wang2024translation} uses LangGraph as a router. It reads the input and hands it to a translation agent for English, French or Japanese, each built on a model such as GPT-4o. As an example of routing in LangGraph, it is neat and concrete. The testing is thin, though. Only a few languages are covered, and the system depends on a paid model.

\section*{Summary}

Read in order, the papers tell a story. ReAct taught agents to act. Reflexion taught them to learn from mistakes. AutoGen let them talk, and MetaGPT made them follow procedures. But the same problem keeps coming back. Either the flow is rigid and cannot branch or loop, or it is handed to the model and becomes hard to control. What was missing was a way for the developer to lay out the allowed paths, with shared state and room to retry, while the model still does the clever part of each step. That is the gap LangGraph, and the LangGraph+CrewAI pairing, set out to fill.

\chapter{Materials and Methods}

Nothing in this work is trained, and no dataset is involved. So ``materials'', for this chapter, simply means the software the system is put together from. I go through those pieces one by one and finish with the yardsticks the paper applies to its own results.

\section{LangGraph: Core Concepts}

LangGraph builds LLM apps as graphs that keep state between steps \cite{langgraphdocs}. The base paper points to three things it adds over other LLM frameworks: loops, close control over the flow, and memory that survives from one step to the next \cite{duan2024langgraphcrewai}. It can run one agent or many, in a hierarchy or in sequence. Its pieces are listed below and drawn in Fig.~\ref{fig:graph}.

\begin{itemize}
    \item \textbf{State} is the shared data, usually a typed dictionary. Every node reads it and updates it. A reducer can say how an update is merged, for example adding a new message to a list instead of replacing the list.
    \item \textbf{Node} is just a Python function. It does one step, such as calling the model or a tool, and returns the part of the state it changed.
    \item \textbf{Edge} is a fixed move: after node A, run node B.
    \item \textbf{Conditional edge} is a small router function that looks at the state and picks the next node. Branches and loops are made from these.
    \item \textbf{START and END} mark where the graph begins and finishes.
    \item \textbf{Checkpointer} saves the state after every step. That means a run can be paused, inspected, picked up again after a crash, or held until a person approves it.
\end{itemize}

Building a LangGraph app takes five steps. Define the state. Add nodes. Connect them with edges. Compile. Run. The tiny example below answers one question with one model call.

\begin{lstlisting}
from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class State(TypedDict):          # 1. define the state
    question: str
    answer: str

def answer(state: State):        # 2. a node is a plain function
    return {"answer": llm.invoke(state["question"])}

g = StateGraph(State)
g.add_node("answer", answer)
g.add_edge(START, "answer")      # 3. connect the edges
g.add_edge("answer", END)
app = g.compile()                # 4. compile
app.invoke({"question": "What is LangGraph?"})   # 5. run
\end{lstlisting}

\section{CrewAI Framework}

CrewAI \cite{crewaidocs} is an open-source framework for agents that play roles and work on a problem together. You give each agent a role, a goal and some tools. There are four pieces:

\begin{itemize}
    \item An \textbf{agent} does the work. It decides things and can talk to the other agents. You define one by writing its role and goal, plus a short backstory.
    \item A \textbf{task} is one job. It comes with a description, names the agent responsible, and lists the tools that agent may use.
    \item A \textbf{tool} is anything an agent can use, such as reading email or searching documents.
    \item A \textbf{crew} is the team of agents plus the process that decides the order of their tasks.
\end{itemize}

The models behind CrewAI can be hosted ones, OpenAI's for instance, or local ones served through Ollama \cite{ollamadocs}. Roles are written by the developer. When one agent finishes, CrewAI passes the work on to the next without extra code \cite{crewaidocs}. It was built for jobs that take several steps and need a decision or two on the way.

\section{Evaluation Criteria}

The base paper is exploratory. It has no accuracy figures, and nothing on speed or cost either. What it does instead is judge LangGraph+CrewAI on four qualities, and since there is nothing better to go on, I borrow the same four for this report:

\begin{itemize}
    \item \textbf{Control}: can the developer define and restrict the flow?
    \item \textbf{Information flow}: how easily do results pass between steps and agents?
    \item \textbf{Collaboration}: how well is the work split among agents with different roles?
    \item \textbf{Extensibility}: how easily can existing tools and agents, such as LangChain ones, be plugged in?
\end{itemize}

\chapter{Methodology}

\section{Design Rationale}

The paper starts from a plain observation. One LLM agent cannot cope with a complex task on its own. A team of agents can, but only with two things in place: tight control of the flow, and good teamwork \cite{duan2024langgraphcrewai}. So the authors split the job. LangGraph's graph handles the control and carries information between agents. CrewAI's crews handle who does what. The paper then asks two questions. How should agents be designed on LangGraph so the flow is precisely controlled? And how can CrewAI make those agents good at more kinds of task?

\section{System Architecture}

There are two layers, and they meet at the shared state (Fig.~\ref{fig:arch}).

\begin{itemize}
    \item \textbf{LangGraph is the control layer.} The user's task enters the graph. Nodes stand for agent steps. Edges, some of them conditional, decide which step runs next, and the state carries data along.
    \item \textbf{CrewAI is the team layer.} Inside a node, a crew does the real work. Each agent has a role and a goal, tasks are handed out, and the agents combine their results into the node's output.
\end{itemize}

\section{Integrating LangGraph with CrewAI}

Why combine them at all? The authors' answer is that a hard task becomes easier to manage once the graph handles the flow and a crew handles the people, so to speak. The combined system can also be wired to tools a team already uses. Because CrewAI gives each task one owner, it is always clear who did what. And since CrewAI talks to LangChain, agents someone has already written in LangChain can be reused as they are \cite{duan2024langgraphcrewai}.

Put simply:
\begin{itemize}
    \item \textbf{LangGraph owns the flow}: the order of steps, the branches, the loops and the state.
    \item \textbf{CrewAI owns the teamwork}: which agent takes which task, and how they cooperate.
\end{itemize}

\section{Workflow}

Fig.~\ref{fig:workflow} follows one task through the system. LangGraph takes the task and sends it to a node. The crew in that node does the work and writes the result back to the state. Then a conditional edge asks one question: are we done? If not, the flow moves on to the next step. If yes, the graph ends.

\section{Worked Example: Automatic Email Handling}

The authors borrow the email example from CrewAI's documentation and rebuild it on LangGraph+CrewAI \cite{duan2024langgraphcrewai}. The job is cut into small steps that run on their own.

Fig.~\ref{fig:email} shows the graph. It starts at \texttt{check\_new\_emails}. If new mail has arrived, a conditional edge sends it to \texttt{draft\_responses}. If not, it goes straight to \texttt{wait\_next\_run}. After the wait, the graph goes back and checks the inbox again. That last loop is the interesting bit. It turns a script that runs once into an assistant that keeps going, and a plain chain simply cannot express it.

The code behind the graph (Fig.~\ref{fig:code}) follows the same five steps as Chapter~3. Look at the \texttt{draft\_responses} node. Its function is \texttt{EmailFilterCrew().kickoff}. In other words, a whole CrewAI crew runs as a single LangGraph node. When I first read the code, this one line made the whole design click for me.

from langgraph.graph import StateGraph
from .state import EmailsState
from .nodes import Nodes
from .crew.crew import EmailFilterCrew

class WorkFlow():
    def __init__(self):
        nodes = Nodes()
        workflow = StateGraph(EmailsState)
        workflow.add_node("check_new_emails", nodes.check_email)
        workflow.add_node("wait_next_run", nodes.wait_next_run)
        workflow.add_node("draft_responses", EmailFilterCrew().kickoff)
        workflow.set_entry_point("check_new_emails")
        workflow.add_conditional_edges(
            "check_new_emails",
            nodes.new_emails,
            {"continue": 'draft_responses', "end": 'wait_next_run'})
        workflow.add_edge('draft_responses', 'wait_next_run')
        workflow.add_edge('wait_next_run', 'check_new_emails')
        self.app = workflow.compile()

\chapter{Results and Performance}

Do not expect tables of numbers here. The base paper reports worked cases rather than experiments: it builds two multi-agent apps with LangGraph+CrewAI, shows that they run, and says what the pairing made better. I take the two cases in turn. After that I pull out the main findings, and I end the chapter by asking how much these results actually prove.

\section{Application Case 1: Code Generation with Code Review}

The first case writes code and then reviews it (Fig.~\ref{fig:codegen}). A question goes into a \emph{code generation} node, which writes the code. A \emph{code check} node tests it. If the test fails, the flow goes back to generation, this time with the error attached. If it passes, the code is the answer. Each attempt's status and feedback travel through the shared state as they happen, and the authors say this made code generation more efficient \cite{duan2024langgraphcrewai}. Reflexion and ReAct argue for exactly this write, test and fix cycle. The difference is that here the loop is a real edge in the graph that you can see and inspect, not something left to the model's judgement.

\section{Application Case 2: Automatic Work-Order Processing}

Case two is about work orders. These are the tickets an IT or maintenance desk sees all day (Fig.~\ref{fig:tickets}). First an Ollama embedding model turns the ticket text into a vector. The vector goes into FAISS, which makes it quick to pull up old tickets that look similar. Then a few CrewAI agents, one per task, read the ticket closely and pass their notes to each other. The authors say the agents understood tickets better this way, and got through them faster \cite{duan2024langgraphcrewai}.

\section{Key Findings}

The authors draw four conclusions from these cases:
\begin{itemize}
    \item \textbf{Information flows better.} The graph structure makes it easy to pass results between agents.
    \item \textbf{The flow is under control.} Building agents on LangGraph gives the developer a firm grip on the multi-agent workflow.
    \item \textbf{Teamwork improves.} CrewAI's task allocation and resource management make the agents work together better.
    \item \textbf{Harder tasks become possible.} By splitting the work, the agents manage tasks a single agent finds too hard.
\end{itemize}

\section{Discussion}

I think the paper's real strength is that it makes the fit between LangGraph and CrewAI easy to see. The graph decides what happens next. The crew decides who does it. The three cases help, because they are ordinary jobs: sorting email, checking code, handling tickets. Most offices have all three.

But the results need careful reading. The paper has no numbers at all. There are no success rates, no response times, no costs, and no comparison with a single agent or with another framework. So when the authors say efficiency ``improved'', they mean that is what they saw in their cases. No test was run to show it. I would like to see the pairing run on a benchmark, measuring task success, model calls and cost against a single agent and against LangGraph alone. Even without that, the paper is a clear, readable guide to building multi-agent apps where control and teamwork live in separate layers.

% ================================================================== Chapter 6
\chapter{Advantages}

\begin{itemize}
    \item \textbf{Explicit control.} The developer decides which paths exist. The model can fill in a step but cannot invent a new route, so behaviour is easier to predict and to audit.
    \item \textbf{Shared state.} Every step sees the same, current data. Nothing has to be copied between agents or crammed into a prompt.
    \item \textbf{Loops and retries.} A step can repeat until something is true, say until the tests pass. A plain chain cannot do that.
    \item \textbf{Persistence.} The state is saved after each step, so a run can stop, resume and recover from a crash without starting over \cite{langgraphdocs}.
    \item \textbf{Human-in-the-loop.} The graph can pause at any node and wait for a person. That matters before something like sending an email.
    \item \textbf{Easier debugging.} Each node is an ordinary function you can test alone, and LangSmith \cite{langsmith} shows which path a run took.
    \item \textbf{Not tied to one model.} LangGraph and CrewAI both work with several providers, including local models through Ollama.
    \item \textbf{Clear teamwork.} With CrewAI, roles and tasks give every agent a defined job, and existing LangChain agents can join a crew with little extra work.
\end{itemize}

% ================================================================== Chapter 7
\chapter{Disadvantages}

\begin{itemize}
    \item \textbf{Learning curve.} Graphs, typed state, reducers and checkpointers take time to learn. Using two frameworks means learning two sets of ideas.
    \item \textbf{More code for small jobs.} Something a chain does in five lines needs noticeably more setup as a graph.
    \item \textbf{Big graphs get messy.} Once there are many nodes and conditional routes, the flow is hard to picture.
    \item \textbf{Cost and delay.} Loops and several agents mean more model calls. That costs money and makes replies slower.
    \item \textbf{Still depends on the model.} The graph limits the routes, but a bad model output can still choose the wrong one, or do a poor job inside a node.
    \item \textbf{Fast-changing APIs.} Both frameworks change between versions, so code and tutorials go stale quickly.
    \item \textbf{No numbers in the base paper.} The benefits are shown only through cases, so they are not yet backed by measurements.
\end{itemize}

% ================================================================== Chapter 8
\chapter{Applications}

\begin{itemize}
    \item \textbf{Customer support.} A router node works out what a query is about and sends it to a billing agent, a technical agent or a person. The conversation stays in the shared state.
    \item \textbf{RAG question answering.} The graph fetches documents and scores how relevant they are. If they are poor, it rewrites the query and searches again before answering.
    \item \textbf{Code generation and bug fixing.} Write, test and fix in a loop, as in the base paper's code-review case and the authors' later work on automated bug fixing with LangGraph \cite{wang2025bugfix}.
    \item \textbf{Machine translation.} Text is routed to an agent for the right language \cite{wang2024translation}.
    \item \textbf{Data analysis.} Separate agents build and run machine learning pipelines on Apache Spark \cite{wang2024spark}.
    \item \textbf{Multi-agent teams.} Crews for research, writing and review, one role per agent, as the base paper proposes \cite{duan2024langgraphcrewai}.
    \item \textbf{Ticket automation.} Checking, sorting and forwarding work orders, with similar past cases pulled from a vector database.
\end{itemize}

% ================================================================== Chapter 9
\chapter{Conclusion}

LangGraph treats an LLM app as a graph whose steps all share one state. Branching, looping, memory, a point where a person can step in: a chain has none of these, and a graph has all of them. Nor does the developer have to gamble on a fully autonomous agent and hope it behaves. You decide the routes; the model does the thinking along them.

Duan and Wang show how far this goes when you add CrewAI. LangGraph manages the flow and the state. CrewAI organises agents into teams with roles. Between them they handle jobs that one agent struggles with. Their email assistant, code-review loop and ticket system make the idea concrete, and none of them is exotic.

The weak point is the evaluation. Everything rests on cases, not measurements, so the claimed efficiency gains still need proper benchmarks of success rate, cost and response time. It would also be worth testing how these systems behave as the number of agents grows, and how to keep large graphs readable.

More and more teams now build agentic AI this way, as graphs, when they need it to be trusted. After working on this seminar I understand why. Once the structure is written down, a model's mistakes stop being a mystery. You can point to the node where one happened. You can stop it spreading. Then you fix it.

\chapter{Viva Questions and Answers}

\subsection*{Common Viva Questions}
\begin{enumerate}[leftmargin=*, itemsep=6pt]
    \item \textbf{What is LangGraph?}\\
    \textit{Answer:} An open-source library from LangChain for building LLM apps as a graph. Nodes are steps, edges are the moves between them, and all nodes share one state.

    \item \textbf{How is it different from a LangChain chain?}\\
    \textit{Answer:} A chain runs its steps once, top to bottom. A LangGraph graph can branch, loop back, keep shared state and save checkpoints, so it can retry, pause and resume.

    \item \textbf{What are state, nodes and edges?}\\
    \textit{Answer:} The state is the shared data every node reads and updates. A node is a function that does one step. An edge is a move between nodes, and a conditional edge uses a small router to pick the next node from the state.

    \item \textbf{What does a checkpointer do?}\\
    \textit{Answer:} It saves the state after every step. So a run can resume after a crash, be inspected while debugging, or wait for a person's approval.

    \item \textbf{What does CrewAI add in the base paper?}\\
    \textit{Answer:} Teamwork. Agents get roles, goals and tools, and tasks are shared out among them. LangGraph controls the order and the state; a CrewAI crew does the work inside a node.

    \item \textbf{Explain the email example.}\\
    \textit{Answer:} The graph starts at \texttt{check\_new\_emails}. With new mail it goes to \texttt{draft\_responses}, which runs a CrewAI crew; otherwise it goes to \texttt{wait\_next\_run}. After waiting it loops back and checks again.

    \item \textbf{Which other tools did the authors use?}\\
    \textit{Answer:} LangSmith to track runs, an Ollama embedding model to turn ticket text into vectors, and FAISS to store those vectors and find similar ones.

    \item \textbf{How does LangGraph compare with AutoGen?}\\
    \textit{Answer:} In AutoGen the order of work comes out of the agents' conversation, which is flexible but unpredictable. In LangGraph the developer lays out the paths, so it is easier to control and debug.

    \item \textbf{What is the main weakness of the base paper?}\\
    \textit{Answer:} It has no measurements. There are no accuracy, cost or speed figures and no baseline, so the efficiency claims are not yet backed by experiments.

    \item \textbf{Where is LangGraph used?}\\
    \textit{Answer:} Customer-support routing, RAG question answering, code generation and bug fixing, translation, data-analysis pipelines, research and writing teams, and ticket automation.
\end{enumerate}
